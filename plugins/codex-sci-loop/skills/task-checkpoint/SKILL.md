# Task checkpoint

Use the user's task folder (the worktree root in Git), unless they want to keep the discussion in chat. Resolve `../../scripts/checkpoint.py` relative to the directory containing this resolved SKILL.md. Run it with Python 3 in the task folder or pass `--project-root <folder>` after the command. Reuse the task ID (default `main`).

- At a meaningful milestone, change of direction or pause with work outstanding, persist the facts a new conversation could not infer from the deliverables. Keep the user's operative wording and constraints. After changing a deliverable, pass its project-relative path with `--artifact PATH` on the same write. This records its observed size and SHA-256. Use a brief action note for why it changed. Preserve the reason for a consequential choice. Reference existing files instead of copying their contents.
- For a new task, use one write: `start --request-file - --kind action --note 'completed action and artifact' --next 'open action'`, passing the request on stdin. Add `--artifact PATH` for each important changed file. All three fields are optional. On changed requirements, use `revise --from-revision N --request-file -` with the complete effective contract, plus the same optional flags. A revision clears the old next action. For progress within one revision, use `note --kind action --note '…' --next '…'`. Avoid repeating unchanged facts or creating a checkpoint for each turn or compaction.
- After handoff or loss of context, use `show` for the current agreement and next step. For a question about earlier events, use `history --limit 5` directly: it includes the current revision too. Page back with `--before N`, or retrieve one exact contract with `history --revision N --full`. Read again when the revision is unknown, truncated, or a write rejects a stale revision. Earlier modes, checks and actions are historical records.
- Clear a finished action with `note --next ''`. Use `close` for operator-reported completion, `set-state --state paused|blocked|cancelled --reason '…'` for a change of state. Confirm a save only after the command succeeds.

For objective acceptance, declare `--verify-command '…'` at start or revision and run `verify`. In ordinary folders declare each relevant script and input with `--input`. If independent judgment is required, declare `--require-review`, identify the evidence with `show --for-review --full`, then record `review --subject … --reviewer … --outcome … --file …`. Use `finish` to check evidence and pending work. Reopen with `set-state --state active --reason '…'` when necessary. Older phase projects retain their original recovery entry point.
